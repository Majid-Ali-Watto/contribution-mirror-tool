# Performance

A normal run takes a few seconds. Nothing is skipped to get there:

- **Incremental PR/review scan** (`state.py`). After a successful `--apply`, the start time is saved in `api-state.json` (your log folder), for each host separately (a host whose scan failed keeps its own older date and is fully re-checked; the others stay incremental). The next run only asks the host about the period since then, **minus a 3-day safety margin** (a review always updates its PR's `updated` time, and overlap is harmless because duplicates are skipped by timestamp). A **full 365-day scan** is used automatically on the first run, when the mirror is empty, when the work account changes, when that host's projects change (added, removed, paused or resumed), when the state file is missing or unreadable, or with `--full-api` (about 15 s). The state is saved only after the commits are written, and never after a failed API call.
- **Parallel work.** Review lookups use 8 threads over keep-alive HTTPS (no extra process per call). Fetches and temporary clones of all projects run in parallel. Rate limits and 5xx errors are retried, honouring `Retry-After`.
- **No silent search cap.** GitHub search returns at most 1000 results per query. A date range that would exceed it is split in half until each part fits.
- **git does the filtering** (`gitutil.py`). `git log --author=<your email>` (fixed string, any case) sends only your commits to Python, read line by line. The hashes of your commits are kept in memory for the run (to count a commit that is in two listed repos once): a few MB even for tens of thousands of commits.
- **No repeated set-up work.** The account chosen for each host is remembered and reused if it still works (instead of asking the host about every logged-in account each run; `--full-api` compares them again), what a self-hosted server turned out to be is remembered (no probe every run), and the `origin` of each listed repo is looked up in parallel.
- **Optional clone cache.** URL entries are normally cloned again on each run, into the `tmp/` folder of your log folder, and deleted afterwards. With `MIRROR_CLONE_CACHE` set, the clone is kept and only new commits are fetched: much faster for long histories, and for hosts that ignore tree-less clones and send everything. Without the cache, the disk holding your log folder needs room for the largest such project while its scan runs.
- **One `git fast-import`** (`mirror_repo.py`) writes all new commits at once, instead of one `git commit` process each (identical commit metadata, empty tree).
- **No push when nothing changed.** `sync` skips `git push` if `main` equals `origin/main` (it prints `nothing to push`). Unpushed commits from a failed earlier push are still pushed.

In incremental runs the `matching` / `already_mirrored` numbers in the summary only cover the recent PR/review window (commits are always counted in full). `created` is exact.
